# Headless Preview recording, 18 October 2026

Read-only research for `feat/headless-browser-recording`, starting at Tau `f20b0ca3`. No product files changed, browser launched, profile opened, or heavyweight checks run. The implementation decision below comes from official protocol definitions, Chromium implementation and tests, and web specifications.

## Recommendation

Use native `Page.startScreenRecording` / `Page.stopScreenRecording` for the first implementation, with an explicit capability error on an older or unsupported browser. This fits Tau's existing private CDP pipe, avoids an external encoder and avoids adding a second trusted renderer target. Document Chromium 153 as the introduction milestone, then feature-detect the actual command and handle its unsupported-build error. Do not promise that every Chromium 153 build supports it. Retain the existing profile, sandbox and page ownership rules. These are implementation recommendations, not a browser compatibility guarantee.

If support for older installed Chromium is required, use a separate owned blank helper target to encode `Page.startScreencast` frames with canvas `captureStream()` and `MediaRecorder`. That is a larger implementation with its own scheduling, lifecycle and bounded-transfer requirements. Do not install an encoder into the untrusted page or relax its CSP.

## Native command and version evidence

The commands landed in Chromium commit [`cc610ab5f797526e71a0a787823e019cc15dea89`](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89), 7 August 2026, commit position 1675558. At that exact commit, [`chrome/VERSION`](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/chrome/VERSION) says **153.0.7996.0**. That establishes introduction during M153. It does not establish the first distributed Chrome Stable patch or every vendor build's configuration. The current [official Page protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl) still marks both commands experimental.

`startScreenRecording` accepts optional `audio`, `maxWidth`, `maxHeight` and `frameRate`, and returns an `IO.StreamHandle`. `stopScreenRecording` returns a stream handle too. There is no protocol option for codec, MIME type or container. The [initial PageHandler implementation](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/browser/devtools/protocol/page_handler.cc) defaults to no audio, 800 × 600 maximum dimensions and 30 fps. It rejects a concurrent screencast/recording, checks for a top-level active frame and returns an error when stopping without an active recording.

The [native MediaRecorder implementation](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/browser/devtools/protocol/media_recorder.cc#226) explicitly rejects builds without `ENABLE_LIBAOM`. The [encoding service](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/services/devtools_media_encoding_service/devtools_media_encoding_service_impl.cc#68) uses an MP4 muxer, AV1 Main video and optional Opus audio. Thus this path produces **`.mp4`, `video/mp4`**, not WebM or H.264. Chromium's own [stream-helper test](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/third_party/blink/web_tests/http/tests/inspector-protocol/page/resources/stream-helper.js) checks the `ftyp` MP4 signature. AV1 playback compatibility must be checked separately from successful recording.

## Stream reads, EOF and stop

The native recorder appends encoded bytes to a binary `DevToolsStreamFile`. Stop shuts down capture, drains queued encoder work, flushes the MP4 muxer and completes after the encoding service sends `OnClosed`. Start and stop expose the same backing stream in this implementation. [Recorder stop and data callbacks](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/browser/devtools/protocol/media_recorder.cc#472), [encoder flush](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/services/devtools_media_encoding_service/devtools_media_encoding_service_impl.cc#279).

**A live `IO.read` EOF is not proof that recording has finished.** [`DevToolsStreamFile::InnerReadOnFileSequence`](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/browser/devtools/devtools_stream_file.cc#115) returns EOF whenever the requested/current position reaches `last_written_pos_`. Later appends can still add bytes. Before the first append initializes the temporary file, a read can fail with `Read failed`. This is source-derived behavior, not an empirical test here.

The [IO definition](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/third_party/blink/public/devtools_protocol/domains/IO.pdl) supports bounded reads and an optional offset. Omitting offset continues from the previous read position. Decode each response according to `base64Encoded`; the native recording file is binary and returns base64. `IO.close` discards temporary backing storage. The [IO handler](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/content/browser/devtools/protocol/io_handler.cc#57) defaults to 10 MiB per read, so Tau should request a smaller explicit size.

The simplest reliable sequence is:

1. Start recording and retain its stream handle for cleanup.
2. On stop, await `Page.stopScreenRecording` so the encoder and muxer finish.
3. Drain its returned handle in bounded chunks until EOF, enforce a total byte limit and write the final artifact through Tau's existing ownership rules.
4. Close every obtained handle in cleanup, including errors and cancellation.

Chromium's [basic recording test](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/third_party/blink/web_tests/http/tests/inspector-protocol/page/startScreenRecording.js) follows stop-then-drain. Incremental reading is possible but needs a loop that distinguishes a temporary live EOF from final stop, tolerates the initial unreadable file, and never closes the stream prematurely. Reading incrementally does **not** reclaim already written browser-side bytes: the temporary file remains until close. Bound recording duration as well as exported size.

The native muxer does not retain the entire recording in RAM until stop. Its constructor converts the unset output interval to the [minimum forced-output interval of 100 ms](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/media/muxers/muxer.h#33). [Mp4Muxer](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/media/muxers/mp4_muxer.cc#16) tests that interval at video keyframes; the encoding service requests one keyframe every two seconds. [FlushFragment](https://chromium.googlesource.com/chromium/src/+/cc610ab5f797526e71a0a787823e019cc15dea89/media/muxers/mp4_muxer_delegate.cc#417) writes output and clears its fragment list. Therefore a 1.5-second recording may expose only its initial `ftyp` box until stop, while longer recordings can expose completed fragments. This is nominal timing, not a guaranteed two-second byte or memory bound. The encoding service has a queued-frame deque, exposes no recording bitrate or queue limit, and can accumulate work under encoder overload. Incremental reads can enforce an observed encoded-size cap after fragments arrive, but cannot prove a hard browser-memory cap. Keep maximum duration, dimensions and fps conservative; avoid claiming that host-side byte checks bound every browser allocation.

## Older-browser alternative

`Page.startScreencast` emits JPEG/PNG `screencastFrame` events, not a video stream. Acknowledge each accepted frame using its event `sessionId` through `Page.screencastFrameAck`; otherwise backpressure stops further delivery. Its frame metadata supplies capture timestamps. Both startScreencast and its events are also marked experimental in the [official Page definition](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl). It is an established API, but calling it a stable CDP guarantee would be inaccurate. Omit newly added optional parameters on older Chromium.

An encoder helper can decode each frame into its own fixed-size canvas, call `canvas.captureStream(fps)`, and use a feature-tested `MediaRecorder` MIME such as `video/webm;codecs=vp8`. Canvas capture shipped by default in Chrome 52, and MediaRecorder in Chrome 49. [Chrome canvas capture documentation](https://developer.chrome.com/blog/capture-stream), [Chrome MediaRecorder documentation](https://developer.chrome.com/blog/mediarecorder).

The [canvas-capture specification](https://w3c.github.io/mediacapture-fromelement/#dom-htmlcanvaselement-capturestream) requires an origin-clean canvas and only captures when the capture rules permit a frame. The helper should receive encoded screenshot bytes from Tau, not read the source page. Fixed canvas dimensions avoid recording-track changes during navigation or viewport resize. It records video only unless an audio track is separately supplied. Timestamp pacing and repeating the last frame during idle periods need deliberate handling; screencast events are not a constant-rate video feed.

`MediaRecorder.isTypeSupported` is a capability hint, not assurance that encoding will succeed with available resources. Collect all `dataavailable` chunks in order, including the final chunk delivered by stop, and await the stop event before finalizing. Individual chunks need not be playable by themselves; the combined recording must be. [MediaStream Recording specification](https://w3c.github.io/mediacapture-record/#dom-mediarecorder-stop).

The helper-target design is an inference combining these APIs. It has not been verified here in headless Chromium, including background-target throttling, unchanged-frame duration, MIME availability or cleanup after a crash. Tau's current [headless target handling](../../kits/preview/headless-surface.ts) closes newly attached page targets, so an encoder helper would require an explicit owned-target exception. Neither this alternative nor the native path needs a public debugging port, browser download, external ffmpeg or a real user's Chrome profile.
