# External MCP authorization, 18 October 2026

Read-only research for package 09. No runtime, browser, credentials or accounts were used. Recommendations below are Tau design choices, not extra protocol requirements.

## Current specification and supported wire version

The official `latest` authorization specification resolves to **2026-07-28**. It profiles OAuth 2.1 draft 13; OAuth 2.1 itself remains an Internet-Draft, currently [draft 16, September 2026](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/). Pin the MCP profile rather than silently substituting another OAuth draft. [Current MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

Tau declares SDK `^1.29.0`; the installed SDK's `types.js` advertises `2025-11-25` as latest, with older versions, **not 2026-07-28**. The existing endpoint uses its initialize-based server. The new [2026 transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) requires protocol/version metadata mirrored into request headers and no longer uses the older transport session model. Adding OAuth does not upgrade that wire implementation. First release should explicitly support the verified **2025-11-25 transport**, apply the newer authorization protections below, and avoid advertising complete 2026 wire support. Full current-protocol support requires a separate SDK/transport compatibility check. [Tau dependency](../../package.json), [existing endpoint](../../src/main/mcp-endpoint.ts).

## Required authorization behavior

Authorization itself is optional in MCP; once implementing this protected HTTP integration, follow the profile's normative requirements:

- **MUST:** act as an OAuth resource server; publish RFC 9728 protected-resource metadata including `resource` and at least one `authorization_servers` issuer. Provide discovery through a `401` Bearer challenge containing `resource_metadata`, or the well-known route. Implementing both avoids client differences. Publish RFC 8414 authorization-server metadata or OIDC discovery. Clients must support both AS discovery forms. For `/mcp`, the path-specific resource metadata is `/.well-known/oauth-protected-resource/mcp`; root fallback is `/.well-known/oauth-protected-resource`. Do not append well-known paths arbitrarily. [MCP discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery), [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728#section-3).
- **MUST:** OAuth authorization-code flow with PKCE. Advertise `code_challenge_methods_supported: ["S256"]`; require S256 for supported clients, compare its verifier, consume codes once, expire them promptly, and bind each code to client, exact redirect URI, granted scopes and resource. Do not offer implicit/password grants. [MCP security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations#authorization-code-protection), [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636#section-4).
- **MUST:** clients send `resource` on authorization and token requests. Bind and validate tokens against Tau's configured canonical MCP resource; reject another machine, origin or resource. Tokens need not be JWTs: opaque tokens can look up their issuer/resource binding server-side. Bearer credentials belong in Authorization headers on every MCP request, never URL query parameters. Return 401 for absent/invalid/expired tokens, 403 for insufficient scope. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#resource-parameter-implementation), [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707#section-2).
- **MUST:** all authorization-server endpoints use HTTPS. The profile's loopback exception concerns **client redirect URIs**, not a general permission to run the AS over HTTP. Hosted clients also require network reachability and publicly trusted TLS; self-signed machine certificates will not automatically work. [Communication security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations#communication-security).
- **MUST:** validate registered redirects exactly; never wildcard host, path or query. Invalid redirects get a local error, not a redirect to that URI. Native loopback-IP callbacks have the narrow RFC 8252 ephemeral-port exception; keep scheme, IP and path fixed. Public/native clients cannot keep a meaningful distributed client secret. Use the system browser, PKCE and request state. Hosted callbacks use registered HTTPS. Loopback describes the client/browser machine, not a remote Tau machine. [RFC 8252 §§7.3, 8.4](https://datatracker.ietf.org/doc/html/rfc8252#section-7.3).
- **MUST:** validate Origin on incoming MCP requests; reject invalid present Origins with 403. Native/server clients may omit Origin. CORS permission is not OAuth consent or authentication. Configure allowed browser origins explicitly and expose required challenge/protocol headers; never reflect arbitrary Origin with credentials. [Streamable HTTP security](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#security--endpoint).
- **SHOULD:** emit authorization-response `iss` and advertise `authorization_response_iss_parameter_supported: true`; clients must compare a present issuer to their recorded issuer without normalization. State is also recommended. Tau should use short-lived, single-use state/consent records and CSRF protection regardless. [Response validation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#authorization-response-validation).

## Registration, refresh and revocation

Current MCP **SHOULD** support Client ID Metadata Documents, or CIMD. **DCR is MAY and explicitly deprecated**, retained for compatibility. Pre-registration remains a valid mechanism. A small first implementation can require owner pre-registration of a client and exact redirects, document why CIMD is deferred, and omit DCR. This supports selected native and hosted clients, not arbitrary clients that only support DCR. Do not claim universal ChatGPT/Claude compatibility without testing their actual registration behavior. [Current registration rules](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration).

If adding CIMD, require an HTTPS client-ID URL with a path; validate JSON, required fields and exact returned `client_id`; check redirects against that document. Display the requesting client and redirect hostname as untrusted claims, not verified ownership. Client-ID and callback origins need not match under the draft; an explicit trust policy may narrow that. Never auto-consent because metadata fetched successfully.

**Refresh tokens are optional.** First complete flow can issue short-lived access tokens only, requiring authorization again after expiry. If refresh is included, current MCP **MUST** rotate public-client refresh tokens. Keep token-family history, atomically invalidate the old token, bind refresh to the original client/resource/scope, and revoke the active family on replay. RFC 9700 permits sender-constrained tokens or rotation, but the current MCP text explicitly requires rotation. Never expand scope during refresh. [MCP refresh guidance](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#refresh-tokens), [RFC 9700 §4.14](https://datatracker.ietf.org/doc/html/rfc9700#section-4.14.2).

Immediate user revocation is a Tau product requirement. Use opaque, hashed-at-rest tokens plus a grant lookup on **every** request so revoking one client takes effect immediately; cancel its in-flight work too. A signed token checked only by expiry would need additional revocation state. An RFC 7009 revocation endpoint is a useful optional extension to the MCP profile; when implemented it must support refresh-token revocation, should support access-token revocation, and returns 200 even for an already invalid token. Keep it separate from an owner-only command that revokes an entire grant. [RFC 7009](https://datatracker.ietf.org/doc/html/rfc7009#section-2).

## Concrete integration seam

ADR 0022 deliberately confines thread credentials to ephemeral loopback. Preserve that endpoint and its Origin rejection. Adding an independently authenticated external endpoint needs an extending ADR, not widening the existing listener or recycling a thread token. ADR 0020 also forbids deriving caller authority from request data. [ADR 0022](../adr/0022-tau-tools-over-mcp.md), [ADR 0020](../adr/0020-host-command-authority.md).

Extract reusable MCP transport/validation code if useful, but introduce an `external-client` principal and dedicated allowlisted tool providers. Existing providers expect a real `RuntimeSessionInfo`; `tau_list_threads` means a parent's delegated children. A fabricated thread session would inherit authority and wrong semantics. Resolve project/thread targets server-side within the approved grant, then dispatch through normal host authority checks. Scopes must constrain both tool listing and every call, including IDs inside arguments.

Proposed first grant: one machine, selected projects/threads, explicit read scopes for thread summaries/transcripts. Add a separately consented control scope only when its bounded dispatcher is ready. Sending an agent prompt is execution authority even if described as "thread write". Exclude terminals, arbitrary paths, secret requests, access management, extension installation and cross-machine forwarding from the first grant. Tool annotations alone cannot establish authorization.

Reuse [HostAccess](../../src/main/host-access.ts) patterns for hashed secrets, persisted 0600 records, owner approval, audit and revocation, but not its `full`/`read-only` device token or `authenticate` union. Persist a separate client/grant registry. Owner consent must show client, redirect hostname, machine, selected data/actions and expiry; approval must occur through the host-established owner channel. Public authorize GETs and paired non-owner devices cannot approve themselves. Existing [method metadata](../../src/shared/host-method-access.ts) remains the authority for downstream commands.

Attach one HTTP dispatcher before static-file fallthrough on all explicitly supported listeners: main socket HTTP server, network/proxy listeners, and Connect's attached listener. Use a configured issuer/resource origin per publication; never manufacture it from arbitrary Host or forwarded headers. Native access and HTTPS proxy access must hit the same grant checks and exact route definitions. [Socket attachment](../../src/main/host-transport-socket.ts), [network listeners](../../src/main/host-network.ts), [Connect listener](../../src/main/connect-listener.ts).

**Hosted Connect is an additional delivery gap.** Current [relay](../../connect-relay/service.mjs) bridges authenticated custom WebSockets; it does not expose a normal public HTTPS `/mcp`/OAuth route. A hosted MCP client cannot use that private protocol automatically. Deliver hosted support through an explicit HTTPS reverse-proxy publication first, or implement a route-preserving Connect HTTP bridge covering MCP, both metadata paths, authorization, token and revocation. Relay credentials stay private transport credentials; they are never OAuth tokens. Local/remote public URLs must not accidentally share audiences merely because both reach one machine.

## Fetch boundaries and remaining evidence

Pre-registration avoids server-side client-metadata fetches. If CIMD/DCR logo/JWKS fetches are added, enforce an egress boundary: HTTPS only, no userinfo/fragments, resolve all A/AAAA answers, reject private/loopback/link-local/metadata destinations, pin the validated connection address, and revalidate every redirect/DNS resolution. Bound redirects, time, bytes and cache size. Prefer no redirects or remote logos initially. A redirect URI is a browser destination, not something the AS should probe server-side. These concrete controls implement the primary sources' SSRF guidance. [CIMD §§6.5–6.7](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-00.html#section-6.5), [MCP security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#server-side-request-forgery-ssrf).

Still unverified: SDK/provider-client interoperability, external clients' registration methods, TLS/public-origin provisioning and Connect HTTP bridging. No tests were run. Verify code reuse, wrong resource/redirect/issuer, omitted or downgraded PKCE, scope escalation, metadata SSRF/rebinding, owner-consent bypass, revocation during calls, and every supported route before advertising compatibility.
