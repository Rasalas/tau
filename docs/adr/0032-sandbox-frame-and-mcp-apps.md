# ADR 0032: One sandbox frame for interactive agent output; MCP Apps on it

Agents and tools produce interactive HTML: an MCP server's `ui://` view of its result (the MCP Apps extension, `io.modelcontextprotocol/ui`), and later an agent's own page. Tau draws all of it in one core component and serves all of it from one core route. A kit supplies the document and the protocol it speaks with it; core supplies the isolation.

## The frame

- **Route.** Core adds `publishFrame` to the browser-resource capabilities (API 1.51.0). A kit hands over HTML, the origins the document declared and a colour scheme, and gets a capability path back; the client resolves it with `host.resourceUrl(path)`. That is already how a desktop window (`tau-ext://resources/…`), a remote desktop, a browser and a phone reach a host's bytes, so the phone and web client get a URL by the route that exists, with no second token store. `shared-files.ts` stays what it is: local workspace files for the window's own process. The path is a connection-scoped bearer capability valid for ten minutes; the frame loads once and keeps its document, so the lifetime only has to cover the first load. A remounted frame asks again.
- **Isolation.** The document is served with `Content-Security-Policy: sandbox allow-scripts allow-forms; <app policy>`, and the same policy is the first element of the document. The sandbox has no `allow-same-origin`, so the origin is opaque and the page can read neither the workbench's storage nor its host connection. A `srcdoc` frame would inherit the workbench's CSP (`script-src 'self'`) and run nothing, which is why the document needs a URL with its own headers. The app policy follows the MCP Apps spec: `default-src 'none'`, inline script and style, the declared `resourceDomains`, `connect-src`, `frame-src` and `base-uri` only from declared origins (reduced to `scheme://host[:port]`, at most 32), `form-action 'none'`, never `'self'`.
- **Bootstrap.** Core injects, behind the doctype and the policy and before any app script, a colour-scheme script (the document's canvas and native controls follow the workbench, and a later change reaches the frame by message; only the parent window counts) a key script and a cookie guard (`document.cookie` throws in an opaque document; the guard answers an empty string, which is what analytics libraries expect). The key script is the answer to a click giving the keyboard to the document: the client names the Cmd/Ctrl chords of commands that only change the view, and the script passes one back when no text field has focus and the page's own listeners left the key alone.
- **Component.** `SandboxFrame` in the renderer takes a URL and owns: the `sandbox` and `allow` attributes (`allow` only from declared permissions), the message listener (a message counts only when `event.source` is this frame's window; posts go to `"*"`, the only target an opaque origin has), the height (80 to 2000 px, set by the caller from the app's own report, never by the frame), the navigation lock (a second `load` of the same document stops the frame and drops the bridge; the frame can always navigate itself, the lock keeps a page Tau never served from posing as the app), and full screen. Full screen shows the same box in the top layer (`popover="manual"`), because moving an iframe to another parent reloads it and loses the app's state. A key the document passes on is replayed as a keydown on the iframe element, so the window's own listeners see it as they see a key outside; the frame does that only while it has focus and the user's activation is live, and only if the command the app would run for that key is one a page may press (`access: "read"`, and the two that open a draft). The document can claim any key, so a chord of a command that changes a thread never leaves the page. It ends on Escape, on focus outside the box and when the caller asks, which the Codex kit does before it raises an approval. A browser without the Popover API keeps the frame inline.
- **Links** leave a frame only through the caller, and only while the frame has focus and the user's activation is live (`navigator.userActivation`). A frame cannot open a window or navigate the workbench.

## MCP Apps in the Codex kit

- **The bridge is written in the kit** (JSON-RPC 2.0 over `postMessage`, spec 2026-01-26 plus `ui/download-file` and `ui/notifications/request-teardown`), not taken from `@modelcontextprotocol/ext-apps`. Its `AppBridge` needs `@modelcontextprotocol/client` and `core` 2.x and `zod` 4 as peers (about 1.5 MB unpacked), where Tau uses the 1.x SDK; and what it would forward to is Codex's app-server, with an approval in between, so its client forwarding goes unused. The kit's bridge is transport-free and tested against the spec's message shapes. Lift it into core when a second runtime hosts apps.
- **Capture.** The kit declares `extensions: { "io.modelcontextprotocol/ui": { mimeTypes: ["text/html;profile=mcp-app"] } }` in `initialize`. When an `mcpToolCall` item finishes and names a `ui://` resource (`mcpAppUi.resourceUri`, or the legacy `mcpAppResourceUri`), the kit reads it with `mcpServer/resource/read`, keeps the HTML (5 MiB at most, `text/html;profile=mcp-app` only) and the tool's arguments and result, and marks the tool run with a reference. The run carries it in a new generic `extras` field on `UiToolRun`, which a tool card can match on; core knows no MCP App.
- **Storage and life.** The document, its declared policy and the call live in the kit's state folder, one folder per thread, and go when the thread is purged (`threadDeleted`; the trash keeps them for its 30 days). A thread holds at most 40 apps and 50 MiB; the oldest go first. Viewing a stored app needs no live session. Using it does: the tool calls and resource reads of an app go through the thread's `codex app-server`, and a stopped session answers "send a message in this thread to start it again" without starting a turn.
- **Scope of an app's requests.** Every request names the thread and the tool run; the kit resolves the MCP server from the stored run, so an app reaches only its own server. A tool whose `_meta.ui.visibility` excludes `app` is refused.
- **Approvals are prompt cards.** A call to a tool the server does not mark read-only, a `ui/message` and a `ui/download-file` are asked on the thread's own dialog surface (the cards above the composer that Codex's own approvals use), on every client the thread is open on, with the tool's name and the full arguments. The question is asked by the host half of the kit before it acts, so a client cannot skip it. A full-screen app steps back inline first. A message from an app is sent only after the user allowed it, and arrives as that user's message.
- **Model context.** `ui/update-model-context` replaces what that app last said (64 KiB at most). The next turn carries the changed contexts as an extra input item wrapped as untrusted data from the named server, so the model reads it as a report from a tool and not as the user's words.
- **Limits** match the spec's hosts: 256 KiB per message, 16 requests in flight, 25 MiB per download.

## Not decided here

- Agent-written HTML pages (T3's "HTML renders") take the same `publishFrame` and `SandboxFrame`. They need an authoring path for the agent, which is a feature of its own; [ADR 0035](0035-agent-pages-on-the-sandbox-frame.md) is that kit.
- Apps for the Agent SDK runtime: not checked whether its SDK exposes resource reads.
